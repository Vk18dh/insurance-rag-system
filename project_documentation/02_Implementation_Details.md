# PART 11 — LLM PROVIDERS AND FALLBACK
The system uses the `LLMProviderManager` (located in `phase2/services/llm_provider_manager.py`) to handle AI generation. It initializes a chain of providers based on the `.env` configuration. 
**Actual Implementation Sequence:**
1. OpenRouter (Primary Cloud)
2. Groq (Secondary Cloud - Lightning fast LPU inference)
3. Local Ollama (Fallback/Air-gapped)
If Groq returns a 429 Rate Limit or 5xx Server Error, the Manager catches the exception and gracefully fails over to the local Ollama instance (currently locked to `qwen2.5:3b`). 
**Why provider failure is different from low-confidence:** A provider failure is a network/infrastructure issue (e.g., API is down). Low-confidence is a knowledge issue (the AI works, but the document lacks the answer).

# PART 12 — GUARDRAILS
Guardrails are safety checkpoints implemented before the final response is returned to the user.
**VerificationAgent vs Guardrails:** 
- The VerificationAgent checks if the *evidence* is good before generating the answer.
- Guardrails check the *final generated text* to ensure it didn't violate constraints (e.g., admitting it doesn't know, but then hallucinating a guess anyway). 
If a guardrail is tripped, the system triggers a Safe Refusal Flow, preventing unsafe data from reaching the user.

# PART 13 — HITL / HUMAN-IN-THE-LOOP
When the system encounters a highly ambiguous query, contradictory evidence, or extremely low verification confidence, it creates a `ReviewTask` database record via `review_repository.py`. 
**System failure vs Knowledge failure:** The HITL is *only* triggered for knowledge failures. If Ollama crashes (system failure), it throws a 500 error; it does NOT ask a human insurance expert to fix the server. If the AI cannot figure out if a policy covers a specific rare disease (knowledge failure), it flags it for the human expert.

# PART 14 — CITATIONS AND SOURCE GROUNDING
When the ResponseBuilder constructs the answer, the system backend attaches a `citations` array.
**Why the LLM does not invent citation IDs:** LLMs are notorious for hallucinating page numbers (e.g., saying "Page 42" when the document only has 10 pages). Instead, the RetrievalAgent passes the exact database `UUID` of the text chunk. The backend maps this UUID directly to the exact filename (`document_id`) and `page_number` stored during ingestion, guaranteeing 100% accurate citations.

# PART 15 — SECURITY
**Authentication & RBAC:** Handled via JWT tokens. Users have roles (`user` vs `expert` vs `admin`).
**Security Auditing:** `AuditService` logs critical events (like ReviewTask creation) to the PostgreSQL database for compliance.
**Prompt Injection:** The QueryUnderstandingAgent sanitizes input, and `PHASE2__SECURITY__MAX_PAYLOAD_LENGTH` prevents buffer overflow or massive injection payloads.

# PART 16 — DATABASES
1. **PostgreSQL (Application Database):** Stores structured relational data (Users, Conversations, Messages, Review Tasks, Audit Logs).
2. **ChromaDB (Vector Database):** Stores high-dimensional arrays (embeddings) representing the text of the PDFs.
3. **BM25 (Sparse Index):** Stores keyword frequencies in memory/disk.

# PART 17 — FRONTEND TECH STACK
The user interface is built using **Next.js (v16)** and **React 19**. 
- **Styling:** Tailwind CSS (`tailwindcss v4`) and `shadcn/ui` for beautiful, accessible components.
- **Animations:** `framer-motion` (listed as `motion`) and `tw-animate-css`.
- **Icons:** `lucide-react`.
- **Markdown:** `react-markdown` to render the bolding and lists generated by the AI.

# PART 18 — MANAGEMENT SYSTEM
A separate Next.js application (`/management/`) exists for administrators and experts. 
**Features:** 
- **Review Queue:** Experts can view pending `ReviewTask` escalations.
- **Resolution:** They can read the AI's attempted answer, read the source documents, and provide the definitive human answer which is then sent back to the user.

# PART 19 — DOCKER AND INFRASTRUCTURE
The entire system is containerized using Docker Compose.
**Containers actually implemented:**
- `backend`: FastAPI Python server.
- `frontend`: Next.js User UI.
- `management`: Next.js Admin UI.
- `postgres`: Relational database.
- `chromadb`: Vector database instance.
- `ollama`: Local AI model runtime.
They communicate via internal Docker bridge networks, ensuring the backend can securely talk to PostgreSQL and Ollama without exposing them to the public internet.
