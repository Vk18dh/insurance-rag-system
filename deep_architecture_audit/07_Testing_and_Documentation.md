**FUNCTION:** `execute(context: QueryContext)`
**PURPOSE:** Semantically checks if the retrieved text answers the query.
**CODE LOGIC:**
1. Extracts `context.retrieval_result.top_chunks`.
2. If list is empty, returns `confidence=0.0`.
3. Constructs a prompt containing the user query and the chunks.
4. Calls `LLMProviderManager.generate()`.
5. Parses the boolean `is_relevant` and `confidence` from the LLM JSON.
6. Returns `VerificationResult`.
**WHY THIS LOGIC:** It prevents hallucinations by mathematically grading the evidence *before* the reasoning step.

# PART 31 & 32 — "WHY THIS TECHNOLOGY?" (Technically Defensible Answers)
**Q: Why FastApi instead of Django?**
A: FastAPI is built from the ground up for asynchronous I/O (using Python `async/await`). Calling 3 different LLM APIs and a vector database involves heavy network waiting. Django's synchronous nature would block the server.

**Q: Why ChromaDB instead of FAISS?**
A: FAISS is just a library for vector math; it doesn't handle persistence, metadata filtering, or client-server architecture easily out of the box. ChromaDB is a full database system built specifically for RAG metadata.

**Q: Why all-MiniLM-L6-v2?**
A: It's an incredibly small embedding model (under 100MB) that produces 384-dimensional vectors. Larger models like BGE-large require 1024 dimensions, taking 3x more RAM and disk space, which violates our constraint of running locally on consumer hardware, with only a marginal 2-3% gain in retrieval accuracy.

**Q: Why Next.js instead of standard React?**
A: Next.js provides App Router and API routes out of the box, simplifying deployment.

# PART 34 — 15 VIVA QUESTIONS FROM ACTUAL CODE
1. **Q: Which agent runs first?** A: The QueryUnderstandingAgent (cleans and extracts intent).
2. **Q: Where is the embedding model loaded?** A: In the `RetrievalAgent` / Document Ingestion script via `sentence-transformers`.
3. **Q: Why is there a global workflow timeout?** A: To prevent the FastAPI request from hanging forever if the local Ollama LLM freezes.
4. **Q: What happens if the LLM returns malformed JSON?** A: The `LLMProviderManager` regex-strips markdown tags; if it still fails `json.loads()`, the system retries or falls back to the next provider.
5. **Q: Which function creates a ReviewTask?** A: The FastAPI router catches `AgentEscalationException` and calls `ReviewRepository.create()`.
6. **Q: Why does a provider failure not create a HITL task?** A: Provider failure (429/500) is an IT infrastructure error (the network is down). HITL is for *knowledge* errors (the AI doesn't know the answer).
7. **Q: How is duplicate retrieval handled?** A: The Hybrid Retrieval logic merges results from Chroma and BM25 using dictionary keys based on the chunk UUID, summing their normalized scores.
8. **Q: Where is authentication checked?** A: In `backend/app/dependencies/auth.py` via the `get_current_user` FastAPI dependency.
9. **Q: Which agent receives verified evidence?** A: The `ReasoningAgent`.
10. **Q: What happens when the policy isn't in the corpus?** A: Retrieval returns junk, VerificationAgent scores it 0.0 confidence, Orchestrator throws EscalationException, hits HITL queue.
11. **Q: Why are PostgreSQL and ChromaDB separate?** A: Postgres is relational (ACID, users, tasks). Chroma is spatial (geometry, cosine similarity of float arrays).
12. **Q: How are citations mapped?** A: The UUID of the text chunk is deterministic. The backend maps it to `document_id` and `page_number` from the database.
13. **Q: Why is BM25 persisted?** A: It takes a long time to calculate Term Frequency for thousands of pages. Persisting it to disk allows instant startup.
14. **Q: What is the payload limit for?** A: `PHASE2__SECURITY__MAX_PAYLOAD_LENGTH` prevents malicious users from pasting 10,000 words to crash the LLM context window.
15. **Q: How is ambiguity handled?** A: The VerificationAgent detects low confidence due to multiple conflicting answers, triggering the ContradictionAgent, and escalating to HITL.

# PART 37 — FINAL SIMPLE EXPLANATION
**"What happens when a user asks a question?"**
The question hits the backend. The Orchestrator wakes up. It asks Agent 1 to clean the text. It asks the Database to find matching paragraphs. It asks Agent 2 to read the paragraphs and grade if they are actually helpful. If helpful, Agent 3 reasons out the answer. Agents 4 & 5 check for financial risk or contradictions. Agent 6 formats the text nicely. The backend attaches the page number and sends it back to the user's screen. 

**"What happens when confidence is low?"**
Agent 2 (Verification) scores the paragraphs. If the score is too low, the Orchestrator hits the emergency stop button. It saves a snapshot of the conversation to PostgreSQL as a "ReviewTask". It tells the user "I'm escalating this." An expert logs into the Management portal, reads the task, types the correct answer, and hits submit.
